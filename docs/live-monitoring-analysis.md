# Live monitoring and archived-log correlation

Investigation: 4 October 2026. Scope: source review of the auditor, Console reference and web console; offline inspection of six supplied SAZ captures; official Therefore documentation; five subsequent user-supplied screenshots and the user's account of printing document 27953.2. No tenant settings were changed, commands sent, or test events generated by this investigation. The auditor Compose stack was not running when checked. No paired archived-file comparison was performed, so this is not a measured coverage claim.

## Recommendation

Add a continuously running Console collector alongside the existing archived-log collector. Use live observations for early warnings, preserve archives for the configured audit trail, and reconcile the two when files arrive. Do not replace archive ingestion or immediately feed both sources into existing rules as if they were independent business events.

The strongest early benefits are licence problems, repeated operational failures, connector faults/backlogs and monitoring interruptions. Authentication and document-activity rules are also candidates, once their event semantics and coverage are verified. The user's subsequent print example provides concrete evidence of a performed action absent from the displayed Message Viewer despite Print being configured to Log always. Treat printing as unverified for live detection; its appearance in the corresponding archive remains to be checked.

## What links the sources?

The official [Console Window Views documentation](https://help.therefore.net/tf2024/en-us/console/con_r_menu_windowviews.htm) describes the Message Viewer as showing current user/document activity and states that its displayed data is logged to a file, subsequently archived. This establishes an intended relationship. It does not establish a shared event identifier, identical fields, identical filtering or a guarantee that every archived record appears live.

The official [Server Logging documentation](https://help.therefore.net/tf2024/en-us/sd/sd_r_theobject_settings_serverlogging.htm) separately defines configurable event logging: off, success, failure or always. It explicitly includes printing, whose documented default is off. Archive schedules include daily, weekly, monthly and size-based rotation. Consequently, the user's multi-day delay is compatible with the supported configuration; the README's “up to 24h” limitation is too narrow.

Local implementation evidence:

| Property | Archived Server log | Live Message Viewer |
|---|---|---|
| Retrieval | REST query/download of Logfiles documents | SOAP `RefreshConsoleView`, view 3, over `/TheXMLServer` |
| Identity | Tenant + archive DocNo + line number | Tenant/server connection + Key; Key can reset/repeat |
| Time | Second-resolution timestamp parsed with tenant `log_tz` | `TmpStmp`, millisecond-resolution text; web-console README records user confirmation of UTC |
| Actor | Username, host, IP | User and Node fields |
| Operation | Text action | Numeric Oper, mapped through native Console table |
| Outcome | Numeric code plus message-derived success | RetCode plus Text; outcome needs its own validated interpretation |
| Business context | Dedicated document/version/category/workflow columns | No equivalent dedicated columns in the captured schema; some context may be in Text |
| History | Retained archive documents, then auditor Postgres | Bounded server backlog; continuous local persistence required |

There is no demonstrated common unique ID. The archived file's DocNo identifies the log document, whereas an event's `obj_doc_no` identifies the affected business document. Neither is the Console Key.

The operation namespace is not the logging-mask namespace. For example, Console operation 5 is Doc Retrieve, while the auditor's local research identifies logging-mask position 5 as Document New. Do not join numeric values across these domains. Multiple Console IDs can also have the same label: 2 and 201 both map to Disconnect.

## Printing: how to complete the coverage comparison

First check the archive for the user's existing example above. For broader coverage, run a controlled comparison using disposable documents and an explicit action ledger. The existing example supplies a reported real print action and a Console screenshot; the paired archive check and wider client/settings comparison remain outstanding.

1. Record server/client versions, tenant, account, time zone, logging settings, archive schedule and poll health. Start durable unfiltered raw collection before acting.
2. Record a document ID and precise UTC time for each action. Repeat retrieve, new, index change, print, export and delete individually, then include a small burst to check multiplicity.
3. Exercise printing separately in Navigator, Web Client and any other relevant client. Distinguish Therefore's print action from printing an already downloaded file in an external application. Treat the latter as a separate hypothesis; the server may receive no new request.
4. Verify Print is configured to log success/always for the positive test. In a test tenant, compare off/failure/always settings one at a time if determining whether the live feed shares the log mask. Restore settings afterward. Do not infer the print mask position from operation 153.
5. Keep capturing through the action window and await the normal archive. Compare the actual raw file, including its header/server and timestamp range, rather than relying on the archive's GENERATED date alone.
6. Classify each ledger action as both sources, archive only, live only, neither, or inconclusive because of a capture/settings gap. Record one-to-many observations and ambiguity explicitly.

The same matrix should include a controlled failed login, denied document access, workflow activity and a known operational failure where safe. Failed-login tests must stay below lockout thresholds on a disposable account. Record outcome from the action ledger independently of the messages.

For candidate correlation, use tenant, compatible operation, actor, document ID where available, node/IP, time proximity and outcome/text. Calibrate the time tolerance from measured pairs; second-resolution archive timestamps mean exact millisecond equality is unsuitable. Do not merge ambiguous same-second actions. Produce coverage percentages per operation/client/outcome/settings combination only for healthy capture intervals and completed archive windows.

The auditor's CLAUDE.md also records unresolved LogMask read-back discrepancies for New/Retrieve/Change. Therefore settings reads alone cannot settle coverage; actual generated actions and actual records are necessary.

## Which auditor capabilities benefit?

| Detection | Live opportunity | Necessary qualification |
|---|---|---|
| Licence limits | Warn while users are blocked | Validate live code/text mappings; do not misclassify as password guessing |
| Retry storms / recurring failures | Detect active bursts in minutes; retain multi-day recurrence analysis | Validate failure semantics and count units; use short rolling windows for urgent bursts |
| Failed login / success after failures | Earlier warning of suspicious sequences | Prove failed-login visibility and map token/licence cases separately |
| New user/IP / first admin client | Compare incoming activity with archived history | Missing client context is unknown; preserve historical warm-up and known-activity rules |
| Mass deletion | Alert as a verified deletion threshold is crossed | One message is not yet proven to equal one deleted document; prevent archive double counting |
| Restart monitoring | Detect lost/recovered monitoring immediately | Session invalidation or a cursor reset is not proof of Server Start; retain archive restart rule |
| Connector health | Snapshot view 9: rising faults, growing pending work, scheduler state | Compare successive snapshots, not each nonzero count as a new event; baseline existing faults |
| Archive gaps | Explain whether live collection continues while archives are late | Keep separate archive-delay and live-collector-health signals; account for archive schedule |
| Config drift | Poll existing REST settings more frequently | Independent of the message feed; preserve uncertainty in partially mapped mask values |
| Print/export auditing | Potential earlier visibility | Coverage study first; retain archived evidence regardless |

View 5 migration status offers a later extension, but its status semantics need more validation. View 1 active users can enrich licence investigations; it is a snapshot, not a complete login history. The web console already has concrete view-9 handling that is more directly reusable.

Proposed healthy-state target: poll messages every 2–5 seconds, evaluate fast rules every 10–30 seconds, and deliver actionable alerts within roughly a minute after a threshold is met. These are design targets, not measured guarantees. Server emission latency, failures and downstream delivery add delay. Connector polling at the web console's current 30-second cadence is a reasonable starting point to measure.

## Integration design and code impact

1. **Persistent service collector.** Reuse the tested Console protocol/authentication and recovery logic, but run independently of a browser. The web console's 5,000-message buffer, browser-session ownership and inactivity expiry are unsuitable as the auditor's ingestion backbone. Use one owned worker per tenant/endpoint, with a database lease or equivalent to prevent duplicate workers across replicas. Confirm the auditor service account can access Console views; Logfiles read permission does not establish that.
2. **Separate raw observations.** Add durable Console messages, cursors, collector health and snapshot storage in Postgres. Preserve raw Oper/RetCode, unknown fields, server timestamp, receipt timestamp, endpoint identity and mapping version. Retain source-specific identities instead of inventing archive DocNos/line numbers. The existing events schema requires both.
3. **Atomic collection and recovery.** Commit observations and cursor together. Reuse zero-cursor startup/recovery/periodic snapshots, content fingerprints and cursor rollback. Keys reset on restart. Full-payload deduplication has the known limit that truly identical payloads cannot be distinguished. A 501-message response is an observation, not proof of a fixed retention limit or recoverable pagination.
4. **Explicit source and outcome normalization.** Keep unknown outcome distinct from success/failure. Oper's high bit has unresolved meaning. Poll-method success and event outcome are different layers. The web-console code independently verifies short event code 149; it deliberately does not derive every short code from a message-table low word. Do not transplant the archive parser's `failed:` convention into live data without validation.
5. **Source-aware detection and later reconciliation.** Initially retain separate live and archive findings with explicit evidence provenance and link likely related incidents. Enable a shared logical-event representation only for validated mappings. Preserve both observations, but count a confidently matched action once. Where matching is ambiguous, show separate counts rather than sum them. Update the same incident on archive arrival without repeating the initial alert or resetting the human review state.
6. **Durable alert delivery.** Store a notification outbox transactionally with actionable finding changes. Retry delivery with an idempotency key, cooldown and explicit recovery state. Send deterministic alerts first; LLM explanations can follow asynchronously. Do not invoke the daily collection/LLM/digest pipeline on every poll.
7. **Coverage and health in the dashboard.** Show last successful message poll, last new message, oldest retained observation, reconnect history, suspected collection gaps and latest archive coverage separately. An empty successful poll is connectivity evidence, not proof every subsystem is healthy. Historical messages replayed on startup should not trigger a burst of fresh urgent alerts.

Specific existing code constraints:

- `auditor/collector.py` and `migrations/001_init.sql` assume archive-file provenance. Live observations need their own storage/evidence route or an explicit schema redesign.
- `rules/builtin.py` mixes rules restricted to `source='server'` with rules that count all matching events. Simply inserting live rows either excludes them from some rules or double-counts them in others.
- `parsers.py` derives archive success from message text/action when a numeric code exists. It is not a general live outcome decoder.
- `pipeline.py` evaluates broad daily windows and couples ingestion, triage and digest. Extract a fast evaluation path with bounded windows and late-arrival handling.
- `scheduler.py` performs six hourly catch-up attempts after the daily job; catch-up runs disable digest delivery. Faster ingestion alone therefore does not provide timely notification.
- `rules/engine.py`'s `realtime` flag means “compare against now outside backfill”; it does not mean continuous collection. Existing finding dedupe is useful, but does not deduplicate underlying observations.
- `log_gap` uses the last archived event time and a fixed 48-hour threshold. Schedule-aware archive freshness and separate poll health would make this more informative, especially on quiet or weekly/monthly tenants.

## Suggested delivery sequence

**First: evidence pilot.** Add durable shadow collection for one test tenant, with alerts disabled. Run the action matrix and retain at least two actual archive cycles, including the longer connector cycle if testing connector-log correlation. Report measured overlap, ambiguous pairs, latency, restart recovery, service-account permissions and collector-generated traffic.

**Second: operational alerts.** Enable collector health, connector fault/backlog transitions, and validated licence/retry failures. Keep daily digests and archive ingestion. Test crash/restart recovery and notification retries with offline fixtures.

**Third: shared activity/security rules.** Promote only verified mappings to early authentication, deletion, printing/export and other audit detections. Preserve an explicit coverage matrix by server/client version. Archived ingestion remains required even when a live rule is enabled.
